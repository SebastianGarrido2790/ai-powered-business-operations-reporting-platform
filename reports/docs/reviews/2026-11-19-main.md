## Major

### 🟠 Oversized XLSX is parsed before the size limit is enforced, `src/app/modules/sourcing/api/ingestion_routes.py:72`

**Problem**: `_validate_upload` calls `_validate_workbook`, which opens the upload with `openpyxl.load_workbook`, before `acquisition.acquire` enforces `max_upload_bytes` (default 50 MiB). A caller with `sourcing.ingest` can send a workbook larger than the limit and force a full parse, then receive `413`. The size gate does not protect the parse.

**Why it matters**: A crafted or merely large workbook (zip compression bomb, many rows or sheets) can consume CPU and memory before the limit rejects it. This is an authenticated endpoint, which narrows exposure, but the documented 413 ceiling stops being a ceiling for XLSX input. The existing oversize test uses a CSV, so this path is untested.

**Suggested fix**: Add a cheap size guard before the workbook check. `UploadFile.size` is available after multipart parsing; reject with the existing `payload_too_large` 413 when it exceeds the configured limit. Keep the read only workbook check after that guard. If the owner prefers to keep the approved decision 3 ordering unchanged, record the accepted risk explicitly. This is an approved decision, so the finding is about the ordering's side effect, not about removing the check.

## Minor

### 🟡 Blocking file reads and workbook parsing run on the event loop, `src/app/modules/sourcing/api/ingestion_routes.py:129`

**Problem**: `submit_file` is `async def`, but `_validate_upload` (including `openpyxl.load_workbook`) and `acquisition.acquire` (a synchronous 64 KiB read loop and file writes) run directly in the coroutine. FastAPI runs `async def` handlers on the event loop, so a 50 MiB upload blocks every other request in the process for the duration.

**Why it matters**: A single large upload stalls unrelated health, read, and submission requests. At M2 scale this is survivable, but it is a predictable latency spike and a trivial denial of service amplifier from an authenticated account.

**Suggested fix**: Offload the blocking work with `starlette.concurrency.run_in_threadpool`, or split the blocking portion into a synchronous helper. Keep `await get_current_identity(request)` in the async path.

### 🟡 The engine is not disposed when a startup hook raises, `src/app/main.py:43`

**Problem**: The module hook loop runs before the `try: yield ... finally: engine.dispose()` block. If a module's `on_startup` raises, the function exits before entering the `try`, so the engine is never disposed. The contract says modules must not raise, and the Sourcing hook catches everything, but the platform comment says it deliberately does not swallow a raising hook.

**Why it matters**: A third party module that raises, or a future change to the Sourcing hook, aborts startup and leaks the connection pool. In a restart loop this can exhaust database connections.

**Suggested fix**: Put the hook loop inside the `try` so the existing `finally` always disposes the engine, or add a dedicated `try/finally` around the hooks.

### 🟡 Multipart form fields lack the bounds the JSON schema enforces, `src/app/modules/sourcing/api/ingestion_routes.py:134`

**Problem**: `source_id: Annotated[str, Form(...)]` and `entity_types: Annotated[list[str], Form(...)]` have no `max_length` or non empty item validation, while `IngestionCreateRequest` caps `source_id` at 100 and requires a non empty `entity_types`. A multipart caller can send unbounded strings that are only compared against the registry.

**Why it matters**: It is an input consistency gap, not a leak: the values are not echoed, and unknown sources return `404`. Still, the two submission routes should enforce the same request contract.

**Suggested fix**: Mirror the JSON schema limits on the form parameters (`max_length` on `source_id`, and reject blank entity type items), or document why the form route is intentionally looser.

### 🟡 The skip summary discards the protected reference count, `src/app/modules/sourcing/acquisition/cleanup.py:60`

**Problem**: When the final page is full, `sweep_landing` returns `SweepResult(skipped=True, protected_refs=0, removed=0)` even though it has already collected `protected`. The startup log then reports `protected_refs=0`, which reads as "no non terminal runs" rather than "more than the bounded read could prove".

**Why it matters**: The log is the operational evidence for a skipped sweep. Reporting 0 protected refs is misleading when the skip happened precisely because there were too many.

**Suggested fix**: Return `protected_refs=len(protected)` on the skip path, or add a distinct field such as `observed_refs` so the log distinguishes "none" from "too many to prove".

### 🟡 The same missing run condition has two error codes, `src/app/modules/sourcing/api/issue_routes.py:49`

**Problem**: `GET /ingestions/{id}/issues` returns `code: not_found` for an unknown run, while the adjacent `GET /ingestions/{id}` returns `code: ingestion_not_found`. SDD 006 §14 lists `not_found` for an unknown run, so the issues route follows the spec and the older detail route does not.

**Why it matters**: Clients that branch on `code` must handle two values for the same condition on sibling routes. The older code is existing, so this is a consistency note, not a Stage 7 regression.

**Suggested fix**: Harmonize on `not_found` for unknown runs, or document that `ingestion_not_found` is the SDD 002 contract and is retained for compatibility.
